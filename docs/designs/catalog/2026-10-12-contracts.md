This document is the normative contract for the Catalog service. The implementation must generate and validate an OpenAPI 3.1 document and AsyncAPI/JSON Schema artifacts from these definitions before the first code release.

## Contract Principles

- Public synchronous APIs use REST + OpenAPI 3.1 under `/api/v1/catalog`.
- Service-to-service APIs use REST + OpenAPI 3.1 under `/internal/v1/catalog` and require workload identity/mTLS. They are never exposed through the Angular route table.
- Events use the platform envelope and JSON Schema/AsyncAPI. Delivery is at-least-once; consumers deduplicate by `eventId`.
- Catalog IDs are UUID v7 strings. Timestamps are ISO-8601 UTC strings. Money is a nonnegative `int64` VND amount in minor units, where `amountMinor` is the integer VND amount.
- Every public request is authorized through the current Identity decision. JWT role/branch claims and client-provided tenant values are hints only, never the source of authorization.
- Tenant context is derived from the authenticated Identity context. Catalog does not introduce an `X-Active-Tenant-Id` header and never accepts tenant ownership from a body or query parameter. `X-Active-Branch-Id` is accepted only as a server-validated branch selector.
- P0 menu state and base prices are tenant-wide. A branch header is still required for branch-scoped roles so that membership and branch access are checked even when the returned P0 menu graph is global.
- There is no hard delete in P0. Archive/state transitions preserve IDs needed by historical Order and Inventory references.

## Common HTTP Contract

### Headers

| Header | Required | Meaning |
|---|---:|---|
| `Authorization` | Protected public APIs | `Bearer <Cognito access token>`. Cognito authenticates the user; Identity resolves current membership and permission. |
| `X-Correlation-Id` | Recommended | Caller correlation value; generated by the service when absent. Returned in success/error metadata. |
| `X-Active-Branch-Id` | Branch-scoped role/read | Client-selected branch; validated against current active membership. Never trusted alone. Optional for tenant-wide Owner operations and Manager mutations. |
| `Idempotency-Key` | Retryable POST/state mutation | Client-generated key scoped to actor + tenant + operation. Same key must carry the same request hash. |

| `Content-Type` | Request with body | `application/json; charset=utf-8`. |

| 409 | `last_active_variant` | Operation would leave an active item without an active variant/default. |
| 409 | `invalid_required_modifier_rule` | Operation would make a required modifier group impossible. |
| 409 | `duplicate_request` | Same idempotency key was reused with a different request hash. |
| 409 | `archived_resource` | A terminal archived resource cannot be mutated. |
| 422 | `validation_error` | Payload, field or business rule validation failed. |
| 422 | `invalid_modifier_selection` | Selected option is foreign, inactive, duplicated or violates min/max. |
| 422 | `invalid_variant_selection` | Variant is missing, inactive, foreign or ambiguous under legacy resolution. |

| 503 | `authorization_unavailable` | Identity authorization could not be resolved safely; fail closed. |
| 503 | `service_unavailable` | Catalog or a required internal dependency is temporarily unavailable. |

Error messages are safe for clients. SQL details, JWTs, secrets, raw PINs and full request payloads are never returned or logged.

## Authorization and Scope Contract

Catalog sends a decision request to Identity for the current subject, selected tenant context, optional branch context and one of the following permissions:

| Permission | Roles | Scope | Catalog use |
|---|---|---|---|
| `catalog:read` | Owner, Manager, Cashier, Kitchen | Tenant plus validated branch membership for branch roles | POS and admin reads. |
| `catalog:manage` | Owner, Manager | Tenant-wide; Manager needs any active Manager membership in the selected tenant | Categories, items, variants and modifiers mutations. |
| `catalog:resolve` | Order workload identity | Validated tenant/branch request, no end-user role | Private Order resolution. |

Rules:

1. Owner can read/write the selected tenant without a branch header.
2. Manager may read/write the shared tenant menu when Identity confirms an active Manager membership at any active branch in that tenant. A supplied branch header is validated but does not narrow the Catalog mutation; the mutation is audited as tenant-wide.
3. Cashier and Kitchen require an active branch membership and are read-only.
4. The historical/internal resolver can resolve archived references only when the caller is an authorized Order workload. It must not make archived resources sellable.
5. A failed or unavailable Identity decision fails closed. Cached authorization cannot outlive the Identity contract's allowed decision TTL.

| Field | Type | Required | Constraint |
|---|---|---:|---|
| `sku` | string | yes | 1–64, normalized uppercase, tenant-unique and reserved after archive. |
| `name` | string | yes | 1–200 Unicode characters after trim. |
| `categoryId` | UUID | yes | Active category in the same tenant. |

### Variant schemas

```json
{
  "name": "LARGE",
  "price": { "amountMinor": 39000, "currency": "VND" },
  "isDefault": false,
  "displayOrder": 1
}
```

`amountMinor` must be an integer `>= 0`; only `VND` is accepted in P0. A variant cannot be archived or disabled if doing so leaves an active item without an active variant/default, unless the same transaction selects a replacement or changes the item state.

### `CreateModifierGroupRequest`

```json
{
  "name": "Topping",
  "minSelections": 0,
  "maxSelections": 3,
  "displayOrder": 20,
  "options": [
    {
      "name": "Trân châu",
      "priceDelta": { "amountMinor": 5000, "currency": "VND" },
      "displayOrder": 0
    }
  ]
}
```

| Field | Type | Constraint |
|---|---|---|
| `name` | string | 1–120 characters; tenant-unique among active groups ignoring case. |
| `minSelections` / `maxSelections` | int32 | `0 <= min <= max <= active option count`; `min >= 1` means required. |
| `options` | array | At least one option for a group that is attached to an active item. Names are unique within the group. |
| `priceDelta.amountMinor` | int64 | Nonnegative in P0; negative discounts and per-option quantity are not supported. |

`UpdateModifierGroupRequest` can change defaults, name and display order. It cannot silently invalidate an attached active item. Option create/update uses `name`, `priceDelta`, and `displayOrder`; option IDs are never reused.

### `AttachModifierGroupRequest`

```json
{
  "minSelections": 1,
  "maxSelections": 2,
  "displayOrder": 30
}
```

Both override fields are optional. If absent, the group defaults apply. Effective values must satisfy `0 <= min <= max <= active option count`. An attached required group must have enough active options; otherwise the request fails with `invalid_required_modifier_rule`.

### `ChangeStateRequest`

```json
{
  "status": "INACTIVE",
  "reason": "Temporarily out of menu"
}
```

`status` transitions are:

- Category: `ACTIVE -> INACTIVE -> ACTIVE`, or `ACTIVE/INACTIVE -> ARCHIVED` only when no non-archived item remains.
- Item, variant, modifier group and modifier option: `ACTIVE <-> INACTIVE`, then `ARCHIVED` terminal.
- `ARCHIVED` cannot be reactivated or edited.

## POS Read and Cache Contract

`GET /api/v1/catalog/items?view=sellable` and item detail return:

- `ETag: "catalog-tenant-<tenantId>-v<catalogVersion>"` for the tenant-wide P0 graph.
- `Cache-Control: private, max-age=30` for POS reads; the client must revalidate after a mutation event or on expiry.
- `304 Not Modified` when `If-None-Match` matches after current authorization succeeds. Authorization runs before returning `304`.

The cache key is `(tenantId, branchId-or-tenant, view, filters, catalogVersion)`. Branch ID stays in the key for authorization isolation even though P0 prices/menu are global.

Catalog returns a variant only when category, item, variant and every required modifier rule are active and valid. Inventory stock is not folded into Catalog's response. A POS may display a stock-unavailable marker from Inventory, but Order owns the final fulfillment decision.

## Idempotency and Optimistic Concurrency

- Idempotency records are scoped to `(tenantId, actorOrWorkloadId, operation, idempotencyKey)` and store a request hash plus the original status/body reference.
- Replaying the same key and canonical request returns the original result without a second mutation or outbox event. A new key creates a new mutation.
- Reusing a key with a different canonical request returns `409 duplicate_request`.
- `If-Match` compares the resource version for item/category/group/variant mutations. A mismatch returns `409 catalog_version_conflict` and includes the current version/ETag in safe response metadata when available.
- A successful mutation increments the resource version and the tenant `catalogVersion` in the same database transaction.
- A transaction that changes multiple related resources emits one coherent event after commit with the final tenant catalog version. No consumer is required to observe intermediate invalid states.

## Event Contracts

### Common Envelope

```json
{
  "eventId": "0192b2d0-7f30-7abc-8d2c-123456789012",
  "eventType": "catalog.item.changed",
  "eventVersion": 1,
  "occurredAt": "2026-10-12T08:10:00Z",
  "producer": "catalog-service",
  "tenantId": "0192b2d0-7f1d-7abc-8d2c-123456789012",
  "branchId": null,
  "scope": "TENANT",
  "aggregateType": "CATALOG_ITEM",
  "aggregateId": "0192b2d0-7f1e-7abc-8d2c-123456789012",
  "catalogVersion": 18,
  "correlationId": "cor_01J...",
  "payload": {}
}
```

`branchId` is nullable for P0 tenant-wide events. P1 branch-price events set it to the affected active branch. This is an explicit Catalog amendment to the parent event field, which currently assumes every event has a non-null branch.

### Event Types

| Event type | P0/P1 | Payload purpose | Consumers |
|---|---|---|---|
| `catalog.category.changed` | P0 | Category name/order/status and catalog version. | POS cache, Reporting, Audit. |
| `catalog.item.changed` | P0 | Item identity, category, status, SKU, description summary and version. | POS cache, Order cache, Reporting, Recommendation. |
| `catalog.variant.changed` | P0 | Variant identity, item ID, status/default, price and version. | POS cache, Order cache, Reporting, Inventory reference projection. |
| `catalog.modifier-group.changed` | P0 | Group, options, attachment/rule summary and version. | POS cache, Recommendation, Reporting. |
| `catalog.combo.changed` | P1 | Combo composition/state/fixed price. | POS cache, Recommendation, Reporting. |
| `catalog.branch-price.changed` | P1 | Branch override set/removed and effective price. | POS cache, Order cache, Reporting. |
| `catalog.item-metadata.changed` | P1 | Description/tags for AI cold start. | Recommendation/AI projection, Reporting. |

Events are published through the transactional outbox. The payload includes stable IDs and state, not secrets, JWT claims, raw request bodies or unnecessary employee PII. A consumer must use `eventId` for deduplication and `catalogVersion` for stale projection detection.

### `catalog.item.changed` Payload

```json
{
  "changeType": "UPDATED",
  "itemId": "0192b2d0-7f1e-7abc-8d2c-123456789012",
  "categoryId": "0192b2d0-7f1c-7abc-8d2c-123456789012",
  "sku": "CF-SUA",
  "status": "ACTIVE",
  "version": 4,
  "sellable": true,
  "changedFields": ["name", "description"]
}
```

Events use additive evolution within `eventVersion`. Removing/renaming a field or changing its meaning requires a new event version and parallel consumer support during migration.

## P1 Schema Additions

### Combo

`ComboResponse` contains `id`, `name`, `description`, `status`, `fixedPrice`, `components`, `version` and `catalogVersion`. A component contains an item ID, required variant ID and a set of modifier option IDs. The API rejects a combo child, missing required component, inactive component or negative fixed price. Order snapshots the resolved combo structure; it never relies on a later Catalog read to reconstruct a historical order.

### Branch price override

```json
{
  "branchId": "0192b2d0-7f23-7abc-8d2c-123456789012",
  "variantId": "0192b2d0-7f20-7abc-8d2c-123456789012",
  "price": { "amountMinor": 31000, "currency": "VND" }
}
```

There is at most one current override for `(tenantId, branchId, variantId)`. Removing it returns resolution to the tenant variant price. P0 clients ignore this extension and use the tenant price.

### Tags and metadata

Tag slugs are normalized lowercase tenant-unique values; display names are user-facing. `PUT /items/{itemId}/tags` replaces the set atomically. Metadata events are versioned and may be consumed asynchronously by the AI cold-start projection.

## Contract Compatibility and Amendments

| Existing contract | Catalog decision | Required action |
|---|---|---|
| Parent Cashier availability write | Cashier is read-only for Catalog. | Amend parent Catalog auth matrix before implementation. |
| Parent `catalog_items.category` text | Category is a tenant entity referenced by `categoryId`. | Update parent schema/DTO wording. |
| Parent flat `item_modifiers` | Reusable modifier group plus item-group rule. | Replace with group/options/link contract. |
| Parent nullable `OrderLineInput.variantId` | New clients send concrete variant; legacy null resolves only with exactly one active variant. | Add resolver behavior to Order contract tests. |
| Parent event `branchId` required | Catalog P0 events are tenant-wide and use `branchId: null`, `scope: TENANT`. | Make parent envelope branch nullable with explicit scope. |
| Inventory and Catalog availability | Catalog menu enablement is separate from stock. | Order calls Inventory for fulfillment/stock decision. |

No Catalog endpoint grants branch administration, employee management, Order mutation, Inventory mutation or tenant switching.

## Contract Test Matrix

1. OpenAPI validates every request, response, pagination shape, ETag and standard error envelope.
2. Owner and active Manager can mutate tenant-wide Catalog; Cashier/Kitchen receive `403` for every mutation path, including the legacy availability alias.
3. Manager from tenant A cannot read or mutate tenant B using IDs, headers or body references; cross-tenant resources return `404` or `403` according to the shared policy without existence leakage.
4. Missing/revoked membership and unavailable Identity decision fail closed.
5. Stale `If-Match` returns `409 catalog_version_conflict`; concurrent valid updates never expose a half-configured active item.
6. Same idempotency key/request replays the result without duplicate state or events; same key/different request returns `409 duplicate_request`.
7. Item/variant/state endpoints enforce default/last-active invariants and archive terminality.
8. Modifier attach/update validates effective min/max, duplicate selection, inactive options and required-group viability.
9. `GET` sellable read returns an ETag; authorized `304` is allowed while unauthorized `304` is never returned.
10. Resolver accepts valid selections, rejects ambiguous legacy `variantId=null`, returns coherent prices/names/version, and never calls Inventory.
11. Resolver business rejection uses typed `valid=false`; transport/dependency failures use the documented HTTP errors.
12. Event payloads validate nullable P0 `branchId`, stable IDs, catalog version and additive versioning; duplicate deliveries are safe.
13. P1 tests cover combo nesting, branch-price fallback/isolation and tenant-unique tag slugs without affecting P0 clients.
