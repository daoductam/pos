:toc:
:sectnums:

Ngày: 2026-10-13

Các sơ đồ dưới đây là design-level diagrams. Shift service chưa có implementation source trong repository; các service ngoài boundary được biểu diễn theo contracts đã xác nhận.

== Participants

L1 dùng các participant ở system boundary: POS Client, Shift Service, Order/Checkout Saga, Payment Service, Shift PostgreSQL, EventBridge/SQS và Reporting/Audit.

L2 dùng các participant có ý nghĩa kiến trúc trong Shift Service: Controller, Application Service, Admission/Fence Coordinator, Cash Summary/Reconciliation Engine, Shift DB và Outbox/Close Worker.

  pos -> shift: [HTTP/REST] POST /api/v1/branches/{branchId}/shifts
  shift -> db: Lock branch slot + check active shift
  db --> shift: Slot available
  shift -> db: Insert ACTIVE shift + ShiftOpened outbox
  db --> shift: Commit shift A
  shift --> pos: HTTP 201 Shift A ACTIVE
else Cashier B concurrently
  pos -> shift: [HTTP/REST] POST /api/v1/branches/{branchId}/shifts
  shift -> db: Wait for branch slot/unique constraint
  db --> shift: Active shift A exists
  shift --> pos: HTTP 409 shift_already_open
end

shift ->> bus: [EventBridge async] publish ShiftOpened.v1
bus ->> consumers: [SQS async] consume event idempotently
@enduml

participant "Payment Service" as payment
database "Shift PostgreSQL" as db

shift -> db: Lock ACTIVE shift, increment admission_seq
db --> shift: admissionId=A, seq=N
shift --> order: HTTP 201 Admission A
order --> pos: Checkout accepted for processing

par Close races with payment
  pos -> shift: [HTTP/REST] POST close
  shift -> db: Lock shift; phase OPEN -> CLOSING
  db --> shift: closeFenceSeq=N
  shift --> pos: HTTP 202 closeStatus=PROCESSING
else Existing admission completes
  order -> payment: [HTTP/REST] initiate cash payment with admissionId=A
  payment -> shift: [HTTP/REST] POST cash fact/completion for A
  shift -> db: Accept fact seq N; mark admission terminal
  db --> shift: Fact deduplicated/committed
  shift --> payment: HTTP 202/200 accepted
end

order -> shift: [HTTP/REST] New admission after fence
shift -> db: Observe phase CLOSING
db --> shift: Reject admission
shift --> order: HTTP 409 transaction_after_close_fence
@enduml

[plantuml,shift-p0-close-l1,svg]

title P0 Close Shift — L1: System Flow

actor "Cashier / Manager" as user
participant "Shift Service" as shift
participant "Payment Service" as payment
database "Shift PostgreSQL" as db
queue "EventBridge/SQS" as bus
participant "Reporting/Audit" as consumers

user -> shift: [HTTP/REST] POST /api/v1/shifts/{shiftId}/close
shift -> db: Lock ACTIVE shift; OPEN -> CLOSING
db --> shift: Fence committed
shift --> user: HTTP 202 closeStatus=PROCESSING

loop Until all pre-fence admissions terminal
  shift -> db: Read pending admissions <= closeFenceSeq
  db --> shift: Admission state/fact watermark
end

alt Drain complete
  shift -> db: CLOSING/FROZEN -> CLOSED + audit + ShiftClosed outbox
  db --> shift: Commit terminal close
  shift --> user: HTTP 200 CLOSED
  shift ->> bus: [EventBridge async] publish ShiftClosed.v1
  bus ->> consumers: [SQS async] consume close fact
else Drain timeout or unresolved fact
  shift -> db: CLOSING -> PENDING_REVIEW + reconciliation case
  db --> shift: Commit safe review state
  shift --> user: HTTP 200 PENDING_REVIEW
end

payment -> shift: [HTTP/REST] Late fact with admission after fence
shift -> db: Create reconciliation case; no closed-state mutation
@enduml
....

== Design notes

* `CLOSING` và `FROZEN` là internal admission phases; public lifecycle vẫn là `ACTIVE`, `PENDING_REVIEW`, `CLOSED`, `CANCELLED`.
* Close không giữ database transaction mở trong lúc drain. Fence commit trước, close worker xử lý bằng version và idempotency.
* Một cash fact được tính vào expected cash chỉ khi có tenant/branch/shift scope, admission hợp lệ trước fence, source key chưa từng xử lý và trạng thái payment/refund hợp lệ.
* Không có flow tự động reopen shift hoặc sửa count/fact đã submit.
