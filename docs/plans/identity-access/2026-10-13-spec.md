# Feature Spec: Identity & Access P0 Vertical Slice

## 1. Context

`identity-access` là service quản lý danh tính và quyền truy cập cho nền tảng POS đa
tenant. Repository hiện chưa có application source code; implementation sẽ được tạo mới
theo Java 21, Spring Boot và PostgreSQL.

Nguồn thiết kế nghiệp vụ đã được duyệt:

## 2. Goal

Triển khai vertical slice P0 chạy được end-to-end cho:

- Cognito JWT authentication và server-side authorization.
- Tenant bootstrap, branch lifecycle và employee/membership management.
- RBAC `OWNER`, `MANAGER`, `CASHIER`, `KITCHEN` theo tenant/branch.
- Invitation workflow bền vững qua Cognito adapter và worker retry.
- Idempotency, optimistic locking, transactional outbox và audit/event metadata.
- Local development bằng PostgreSQL và Cognito/email adapter fixture.

P1 POS device/PIN quick switch chưa nằm trong implementation slice này. Cấu trúc module
và domain boundary phải để dành extension point nhưng không tạo thêm P1 behavior.

## 3. Actors and Authorization

| Actor | P0 capability |
|---|---|
| Platform admin/bootstrap | Tạo tenant và owner đầu tiên qua protected flow |
| Owner | Tenant-wide branch, employee, membership và role management |
| Manager | Quản lý employee/membership trong branch được gán; không grant role ngang hoặc cao hơn |
| Cashier | Đọc context được cấp; không quản trị membership |
| Kitchen | Đọc context được cấp; KDS permission chi tiết do service khác sở hữu |

Authorization rules:

- Cognito xác thực JWT identity bằng `sub`, `iss`, `aud` và `exp`; Identity DB là source of
  truth cho tenant, branch, membership, role và status.
- JWT scope claims như `tenant_memberships`, `roles` hoặc `branch_ids`, nếu có, chỉ là
  non-authoritative hints cho UI/coarse routing. Không API hoặc downstream service được
  dùng chúng để quyết định business authorization.
- Client-provided tenant/branch/role/user ID không phải bằng chứng ownership.
- Mọi repository query tenant/branch-scoped đều nhận server-side authorization scope.
- Manager không được tạo/promote `OWNER` hoặc `MANAGER`.
- Không được suspend/remove owner cuối cùng nếu chưa có protected transfer/bootstrap flow.
- Membership `SUSPENDED` hoặc `REVOKED` không thể authorize request kế tiếp.

## 4. Selected Approach

### Recommended P0 vertical slice

Tạo một deployable `identity-access` service có hai runtime responsibilities:

1. **API application:** Spring REST/OpenAPI endpoints, JWT resource server, authorization
   resolver và domain commands/queries.
2. **Worker application:** invitation delivery, Cognito adapter, outbox publisher, retry,
   reconciliation boundary và DLQ handling.

Các approach khác đã được cân nhắc:

- Full P0 + P1 ngay từ đầu: loại vì làm tăng security surface và không cần cho MVP.
- Contract-first rồi mới business flow: loại vì repository chưa có runtime skeleton; P0
  cần một vertical slice có thể chạy và kiểm thử được.

## 5. Architecture and Components

```text
API Gateway
    ↓ Cognito JWT + correlation context
identity-access API (Java 21 / Spring Boot)
    ├── Security: JWT issuer/signature/audience/expiry validation
    ├── Authorization: current Identity DB membership resolution
    ├── Tenant & Branch domain
    ├── Employee & Membership domain
    ├── REST/OpenAPI adapters
    ├── PostgreSQL repositories
    └── transactional outbox

identity-access worker
    ├── invitation delivery job
    ├── Cognito/email adapter
    ├── retry/backoff and DLQ boundary
    └── EventBridge/SQS publisher boundary
```

Boundary requirements:

- Không lưu password hoặc tự xây authentication flow.
- API và worker dùng cùng domain/application contracts nhưng có lifecycle và scale độc lập.
- Cognito call không chạy inline trên mọi authorization request.
- Downstream service không query Identity DB; nhận versioned authorization context hoặc
  dùng internal authorization contract.
- Event publication dùng outbox để tránh state/event dual-write.

## 6. P0 Data Flow

### 6.1 Invitation

```text
Owner/Manager
  → JWT + Idempotency-Key
  → validate actor, target role and branch scope
  → transaction:
      create INVITED membership
      persist idempotency result
      persist InvitationRequested outbox event
  → worker calls Cognito adapter
  → Cognito invitation/email delivery
```

Nếu Cognito/email lỗi, membership giữ trạng thái `INVITED`; worker retry bounded với
exponential backoff. Không activate access trước khi Cognito subject được liên kết hợp lệ.

### 6.2 Login and current context

```text
Client → Cognito login → JWT
Client → GET /api/v1/me
      → validate JWT identity claims: sub, iss, aud, exp
      → resolve Cognito sub in Identity DB
      → load current memberships and permissions
      → return tenant/branch/role context
```

`X-Active-Branch-Id` chỉ là branch selector. Server phải kiểm tra selector với membership
primary state cho từng protected operation.

### 6.3 Membership/branch mutation

```text
Authorized actor
  → validate JWT, scope, Idempotency-Key and If-Match
  → transaction:
      update aggregate with optimistic version
      save idempotency result
      save redacted audit metadata/outbox event
  → commit
  → optional consumers invalidate projections/cache
```

Eventual consistency của downstream projection không được kéo dài quyền đã bị revoke;
P0 authorization đọc primary Identity DB state.

## 7. P0 API Scope

Implementation phải cover các contract đã duyệt dưới `/api/v1`:

- `GET /me`
- Tenant bootstrap
- List/create/update/archive branch
- List/get/update employee
- List/get/create/update/suspend/reactivate/revoke membership
- Resend invitation
- `POST /internal/v1/authorization-decisions` cho downstream authorization integration

Mọi retryable mutation dùng `Idempotency-Key`; update dùng optimistic version/`If-Match`.
Response/error envelope, pagination, status code và PII masking tuân theo contracts document.

## 8. Data and Consistency

Identity PostgreSQL sở hữu tối thiểu các aggregate/table family:

- `tenants`
- `branches`
- `users`/Cognito subject mapping
- `memberships`
- `idempotency_records`
- `outbox_events`
- reconciliation/invitation delivery state cần thiết cho worker

Rules:

- ID dùng UUID v7 theo parent convention; Cognito `sub` là opaque external identifier.
- Timestamp dùng UTC; không lưu password hoặc raw token.
- Unique constraints chống duplicate active/invited membership trong cùng scope.
- Mỗi mutation state + idempotency result + outbox record cùng transaction.
- Optimistic locking trả `409 conflict` khi version cũ.
- Migration phải chạy được từ database rỗng, có rollback/repair strategy và seed fixture
  deterministic cho local/demo.
- Không dùng cross-service foreign key hoặc runtime SQL join.

## 9. Error and Failure Behavior

| Condition | Result |
|---|---|
| JWT missing/invalid/expired | `401 unauthorized` |
| Authenticated but outside scope | `403 forbidden` |
| Resource unavailable inside authorized scope | `404 not_found` |
| Invalid input/header/version format | `422 validation_error` |
| Stale optimistic version | `409 conflict` |
| Cognito/email dependency unavailable | `503 cognito_unavailable`, durable retry |
| Rate limit exceeded | `429 rate_limited` |
| Unexpected failure | `500 internal_error`, no stack trace leakage |

Fail-closed behavior is mandatory when Identity DB is unavailable for a protected action.
Retry and DLQ operations must preserve correlation ID, causation ID and idempotency context.

## 10. Testing and Definition of Done

Required test groups:

- Unit: role policy, branch scope, membership state machine, owner invariant and idempotency.
- Repository integration: PostgreSQL migrations, tenant filtering, constraints and outbox.
- API/contract: `/me`, tenant/branch/membership endpoints, headers and error envelopes.
- Security negative: IDOR, cross-tenant, cross-branch, role escalation and stale revoke.
- Cognito adapter: success, timeout, retry, duplicate invitation and reconciliation drift.
- Worker: retry/backoff, deduplication, DLQ and correlation propagation.
- End-to-end: invite → activation → `/me` → branch context → role mutation → revoke.
- Observability: trace propagation and redaction of PII, JWT, token and secret values.

Done when:

- P0 flow runs locally with PostgreSQL and Cognito/email fixture.
- Migrations pass from an empty database.
- All P0 endpoints and authorization constraints have automated coverage.
- Retry cannot create duplicate active membership or duplicate external side effect.
- Outbox preserves events across a committed state mutation.
- Service tests and integration profile pass.
- Service README and implementation walkthrough are present.

## 11. Observability and Security

- Use correlation ID and W3C trace context across API, worker, adapter and outbox.
- Structured logs contain opaque actor/request identifiers, tenant/branch context and
  outcome; never log JWT, access/refresh token, password, raw PIN or unmasked PII.
- Metrics include authorization denials, invitation failures/lag, mutation conflicts,
  Cognito errors, outbox age, retry count and DLQ depth.
- Secrets are runtime-injected through Secrets Manager/configuration; none are committed.
- Validate all input and enforce authorization at API, application and repository boundaries.

## 12. Out of Scope

- P1 POS device registration and PIN quick switch implementation.
- Order, Catalog, Payment, Inventory, Loyalty and KDS business logic.
- Self-managed passwords or a second authentication provider.
- Production Terraform/CDK, full AWS environment provisioning and final CI/CD pipeline;
  these can be planned after the service slice is validated locally.

## 13. Open Decisions for Planning/Implementation

1. Select Spring persistence/migration implementation and package/module layout.
2. Select local Cognito/email fixture strategy while preserving production adapter contracts.
3. Define the implementation details of the canonical authorization context and internal
   workload authentication; the contract is mandatory for P0.
4. Define outbox publisher/runtime topology and EventBridge/SQS local equivalent.
5. Define demo seed data and configuration for rate limits, retry and DLQ.
